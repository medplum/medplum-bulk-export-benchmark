# Medplum Bulk Export Benchmark

Measures how long [FHIR Bulk Data Export](https://hl7.org/fhir/uv/bulkdata/export.html) (`$export`) takes on a [Medplum](https://www.medplum.com) server as the number of patients grows. It loads synthetic patients into a project, runs exports at the system, Patient and Group levels, and records time, resource counts, bytes, and optionally the server's memory and CPU use.

**Run it against a local or dedicated test server, never production.** Loading a large tier writes millions of resources as fast as the server accepts them.

## Requirements

- Node.js 22.18 or later, which runs the TypeScript sources directly
- A Medplum server. For a local server, follow [Run the stack locally](https://www.medplum.com/docs/contributing/run-the-stack).
- A super admin login for that server, to create one project per tier. The local development defaults (`admin@example.com` / `medplum_admin`) are used unless you set `MEDPLUM_ADMIN_EMAIL` and `MEDPLUM_ADMIN_PASSWORD`.

```sh
npm install
```

## Quick start

```sh
# Load 1,000 synthetic patients (33,000 resources) into a new project
npm run load -- --tier 1000

# Export it 3 times at each level
npm run export -- --tier 1000 --level system --runs 3
npm run export -- --tier 1000 --level patient --runs 3
npm run export -- --tier 1000 --level group --runs 3

# Print the results as Markdown tables
npm run report
```

The server defaults to `http://localhost:8103/`. Set `MEDPLUM_BASE_URL` to use another. Every command takes `--help`.

## Commands

| Command                                    | What it does                                                                                                                                                                                |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `npm run load -- --tier N`                 | Creates a project for the tier and loads N patients as transaction bundles. Stop it at any time; re-running resumes without inserting any patient twice.                                    |
| `npm run export -- --tier N --level LEVEL` | Times one export. `system` is `[base]/$export`, `patient` is `Patient/$export`, and `group` is `Group/[id]/$export`. The first group-level run builds a Group of every patient in the tier. |
| `npm run report`                           | Summarizes `results.jsonl`: each load, and the median, minimum and maximum time of each tier and level.                                                                                     |
| `npm run generate -- --patients N`         | Writes the same synthetic data to disk as transaction bundles, for loading with other tools.                                                                                                |

Each tier gets its own project, so a system-level export of the tier contains only that tier's data. Project IDs and client credentials are saved in `state/`, which is gitignored because it holds client secrets. Results are appended to `results.jsonl`, with the server version and client machine details, so results from different machines can be compared.

To use an existing project instead of creating one, set `MEDPLUM_CLIENT_ID` and `MEDPLUM_CLIENT_SECRET` to a client of an empty project before the first `load` of a tier.

## Synthetic data

Each patient has 33 resources, generated by `src/generate.ts`:

| Resource                                                           | Per patient                      |
| ------------------------------------------------------------------ | -------------------------------- |
| Patient, Coverage, AllergyIntolerance, Procedure, DiagnosticReport | 1 each                           |
| Condition, MedicationRequest                                       | 3 each                           |
| Immunization                                                       | 2                                |
| Encounter                                                          | 5                                |
| Observation                                                        | 15 (3 vital signs per encounter) |

Each project also has 20 Organizations and 100 Practitioners, which patients reference as payors, service providers and performers. Resources reference each other the way a real chart does: Observations point to their Encounter, the DiagnosticReport lists its Observations, and so on.

The data is deterministic: patient `i` of tier `N` always has the same content. It is deliberately simple, with codes from a handful of real code systems, so the output is realistic in shape and size (about 700 bytes per resource) without being clinically meaningful. To benchmark a different mix, edit `PER_PATIENT` and `patientEntries()` in `src/generate.ts`.

## How exports are measured

- **Export time** runs from sending the kickoff request until the status endpoint returns the completed manifest. The status endpoint is polled every 100 ms for tiers up to 1,000 patients, 250 ms up to 10,000, and 1 second above that.
- **Download** happens afterwards and is not part of the export time. Every output file is streamed to count its lines (one resource per line) and bytes. Skip it with `--skip-download`.
- **Server memory and CPU** are sampled only when you pass `--server-pid` with the Medplum server's process ID. This reads `/proc`, so it works only on Linux, with the server on the same machine. It records peak resident memory and the CPU time the process used during the export.

## Results

Measured on 2026-10-08, with an earlier version of these scripts that generated the same data profile. Times are the median of 3 runs unless noted.

| Patients | Resources | System | Patient | Group            |
| -------- | --------- | ------ | ------- | ---------------- |
| 100      | 3,427     | 0.48 s | 0.36 s  | 0.37 s           |
| 1,000    | 33,126    | 0.80 s | 0.68 s  | 1.65 s           |
| 10,000   | 330,126   | 3.10 s | 2.31 s  | 16.7 s           |
| 100,000  | 3,300,126 | 21.1 s | 21.1 s  | 19.3 min (1 run) |

- At 100,000 patients, the system-level export wrote 2.17 GB of NDJSON at about 156,000 resources per second. The server's peak memory was about 1.2 GB, and it used about 24 CPU-seconds, essentially one core.
- From 10,000 to 100,000 patients, 10 times the data took 6.8 times as long.
- Group export at 100,000 members needs a Medplum fix that is not yet released. Before it, Group export fails above about 65,000 members, the Postgres limit on query parameters. With the fix it completes, but much more slowly than the other levels, because each chunk of members is searched separately.

Test machine: Intel Core Ultra 9 285K (24 cores), 47 GB RAM, Ubuntu 24.04 on WSL2. Medplum server 5.2.3 as a single Node.js process, PostgreSQL 17 and Redis on the same machine. Postgres was tuned as follows:

| Setting                        | Value |
| ------------------------------ | ----- |
| `shared_buffers`               | 12 GB |
| `effective_cache_size`         | 32 GB |
| `work_mem`                     | 32 MB |
| `maintenance_work_mem`         | 2 GB  |
| `max_wal_size`                 | 16 GB |
| `checkpoint_completion_target` | 0.9   |
| `random_page_cost`             | 1.1   |
| `effective_io_concurrency`     | 200   |

## Loading large tiers

One Medplum server process loads about 1,200 resources per second, limited by a single CPU core. At that rate 100,000 patients (3.3 million resources) takes about 45 minutes, and 1 million patients takes about 8 hours. To load faster on a local test server:

- **Run more server processes.** Start extra Medplum servers on other ports with the same database and Redis, then spread writes across them with `--base-urls http://localhost:8104/,http://localhost:8105/,...` and raise `--concurrency`. Six extra processes reached about 4,300 resources per second.
- **Turn off write caching.** By default every write also stores the resource in Redis. A million patients would need about 46 GB of Redis. Set `cacheResourcesOnWrite: false` in the server config so resources are cached only when read.
- **Watch the dispatch queue.** Every write adds a job to Redis for subscriptions and other background work. If the server's workers can't keep up, the queue and Redis memory grow for the whole load. On a dedicated benchmark server with no subscriptions, `dispatchEnabled: false` makes the workers discard these jobs quickly.
- **Skip the disk flush on commit.** For throwaway benchmark data, Postgres `synchronous_commit = off` speeds up writes. Commits no longer wait for the disk, so a crash can lose the last moments of the load.

Undo these changes before using the server for anything else.
